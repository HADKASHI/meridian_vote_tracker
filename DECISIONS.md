# Decisions

Key decisions and trade-offs. Terms follow [GLOSSARY.md](GLOSSARY.md). The full reasoning behind each decision lives in `.scratch/meridian-vote-tracker/`.

## Stack

.NET 10 (LTS) with ASP.NET Core's built-in OpenAPI 3.1 document and ProblemDetails errors. PostgreSQL 18, Angular 22, and a typed client generated by orval. .NET 8 and 9 both reach end of support on 2026-11-10.

## Data model and history

- **Files are evidence; row records are verdicts.** Every import keeps the original file (with its SHA-256) and one record per line: line number, raw text, outcome, reason, and links to the approved value or conflict it produced. A verdict can't be recomputed from the file later, because it depends on the approved data at the moment of import. The same rev2 line is a *conflict* before Dana's decision and *unchanged* after it. Copying the raw text for every row costs disk only (about one file's size), and it keeps the model uniform and every 7.4 question one query away.
- **Every approved value has exactly one origin:** the import row that brought it in as new, or the conflict decision that approved it. That answers "which file, who uploaded it, who approved it" directly.
- **Only approved data is stored as approved.** Invalid and contradicting values exist only as row records. When a later file sends a clear value for them, it is *new*, not a conflict.
- **Identity is the code.** Member states are keyed by their ISO alpha-3 code. The published country name is kept on the row record only, so "Turkey" vs "Türkiye" can't become a conflict.
- **Changes store only the new value.** History is append-only and ordered by sequence (not timestamp, which can tie or skew), so "previous" is always the earlier entry. The API, not the client, returns "from → to" pairs for positions, weights, country votes and vote details, so every client agrees and nothing redundant can drift.
- **Conflicts and decisions:** a conflict keeps both sides with their origins, and its decision (who, when, comment). A losing simultaneous decision is recorded as "not applied" and shown on the vote's timeline, so nothing is overwritten silently.
- **Membership periods** must not overlap. This is checked in application code, not by a database constraint.

## Scoring rules

Score = 100 × matched weight ÷ counted weight, over the votes where the state voted yes or no (the brief's formula).

- **Abstentions and absences are not counted.** Neither is a stance for or against the position. Half credit or counting them as misses would add an editorial judgement the Institute didn't make.
- **Votes held before or after membership are excluded**, and **"no data"** (a member with no row for a vote) is kept apart from "absent", which the Assembly reported. Each is labelled in the breakdown.
- **Nothing countable means n/a**, not 0, and no rank.
- **Exactness:** matched and counted weights are stored as integers, so every published score can be recomputed by hand. It is displayed to 1 decimal and ranked on the exact value. Exact ties share a rank (1, 2, 2, 4) and are listed by code.
- **No minimum-vote threshold**; every score shows how many votes and how much weight it rests on.

## Roles and concurrency

- **Simplified identity, real authorization.** The user switcher's header feeds a small ASP.NET authentication handler that produces a standard user with role claims. Endpoints are guarded by `Analyst` and `Admin` policies (401/403, ProblemDetails), and an integration test exercises every write endpoint per role. Real sign-in would replace only the handler.
- **Two analysts, one conflict:** the decision is a conditional update ("only if still pending"). Exactly one wins. The other gets 409 with the current state and is recorded as "not applied". Positions use a version for the same reason.
- **Imports are applied one at a time, one vote per transaction**, with the vote locked against concurrent conflict decisions. Otherwise an import could read a value, have it decided underneath it, and open a bogus conflict or miss a real one.
